# CI

The round-trip job does not use `ubuntu-latest`. That label starts moving to Ubuntu 26.04 on 2026-10-19. The workflow pins `ubuntu-24.04` and also runs `ubuntu-26.04`.

ExifTool is Image-ExifTool **13.59**, SHA-256 `668ea3acececb7235fbd0f4900e72d5f12c9b07e5c778fd36cb1e9b5828fd65a`, installed by `scripts/install-exiftool.sh` from the SourceForge release tarball. The 12.76 tarball that generated the fixture bytes returns 404 from exiftool.org and from SourceForge, so the gate cannot pin 12.76. Fixture bytes are not regenerated. Metadata comparisons use this one binary on both the source and the copy.

MinIO stays at `RELEASE.2025-09-07T16-13-09Z`, SHA-256 `7c5bd8512c6e966455b1d198209358b2d191c77a83ab377c4073281065fb855f`, in `scripts/with-minio.sh`. The workflow downloads that binary and runs it. The tree does not contain MinIO source.

rclone stays at **v1.75.2**, zip SHA-256 `349ac8fba6ff65d6247043f1750cdcb518ec5d500ef91463a10d37c0ccdf3702`, in `scripts/install-rclone.sh`. The round-trip job uses that binary as the transport for SFTP and WebDAV (`rclone serve` on a local directory) and for B2. B2 has no local server and no paid account in CI, so that leg is rclone's S3 backend pointed at the same MinIO. The tree does not contain rclone source.

The Android camera-roll job runs on `ubuntu-24.04`. `scripts/install-android-sdk.sh` pins command-line tools `13114758`, SHA-256 `7ec965280a073311c339e571cd5de778b9975026cfcbe79f2b1cdcb1e15317ee`, from `https://dl.google.com/android/repository/commandlinetools-linux-13114758_latest.zip`. It then installs `platforms;android-35` and `build-tools;35.0.0`, which `sdkmanager` checks against Google's repository. `scripts/install-gradle.sh` pins Gradle `8.11.1`, SHA-256 `f397b287023acdba1e9f6fc5ea72d22dd63669d59ed4a289a29b1a76eee151c6`. The library is Android Gradle Plugin `8.7.3` and Kotlin `2.0.21`. `scripts/android-ci.sh` compiles the `backup` library and the `host` app, runs their unit tests (including Robolectric), and assembles the host debug APK. The host test checks the permission decision. It does not click the system permission dialog. A source test fails the job if the main sources delete or update MediaStore. The backup unit tests include `BackupSoakTest`, the same soak the job below prints.

A family-library phone backup is covered on the round-trip job and on the Android unit tests. `receive` starts with `--member`, the Ed25519 public key of a member who has already joined. The test seeds a second member's original and sidecar, uploads as the phone member, and checks that the second member's bytes, mtime, and sidecar SHA-256 are unchanged. A PUT outside `members/<phone-key>/` is refused. `Library::open` on the family library still fails. The Android test drives `WebDavUploader` the same way and names an outside endpoint in the status file and notification 1001. The iOS package test checks the PUT URL, and the simulator job runs the same backup against an in-process receiver, including the surfaced refusal.

[`.github/workflows/backup-scale-soak.yml`](../.github/workflows/backup-scale-soak.yml) runs on a nightly schedule and on `workflow_dispatch`. It also runs a short smoke on a pull request: 8 synthetic items, seed 1, one shard, on an API 30 emulator and on the iOS Simulator. The nightly run is 10,000 synthetic items. One runner does not finish emulator or simulator boot plus a faulted PUT for every item inside the 90 minute job timeout, so that run is 10 shards of 1,000. The seed is the GitHub run id unless the manual run sets one, and each shard writes `faults.log` with the item and the fault. The faults are a socket closed during the body, a pass that stops after that close (the stand-in for a killed worker; the emulator is not rebooted per item), a closed port, and a 201 whose SHA-256 is not the bytes just sent. A later pass uses a healthy receiver. The job summary and the uploaded artifact report verified percent, elapsed time, and time to 99.9 percent. The job fails if `silent_failures` is not 0 or a shard does not reach 99.9 percent. The items are generated bytes in the test cache. The camera roll is not opened, and the receiver is not a family library. A path containing `members/` is refused.

The backup soak job runs on `ubuntu-24.04`. `scripts/android-soak.sh` installs that same pinned SDK and Gradle, runs `BackupSoakTest`, and prints `build/backup-soak-result.txt`. The test repeats backup cycles through the real WebDAV uploader against a loopback receiver. The injected faults are a closed port, a socket closed during the PUT body, a kill that stops the pass during that upload, and a response whose `X-Albumen-Sha256` is not the bytes just sent. A later cycle uses a healthy receiver. The library is 24 synthetic items. The run measured here verified 24 of 24 after recovery, 100.0 percent, with zero silent failures. A silent failure is an attempted item that is still unverified and whose filename is missing from that cycle's status file and from notification 1001. The fault cycles verified 0 of 24, and each of those names was in the status file or the notification. The job fails if that file is missing or if `silent_failures` is not 0. What this run stands in for, and which parts of a 24-hour device backup it leaves out, is in [performance-budgets.md](performance-budgets.md).

The camera-roll emulator job runs on `ubuntu-latest`, which provides KVM. The step writes `/etc/udev/rules.d/99-kvm4all.rules` (`KERNEL=="kvm", GROUP="kvm", MODE="0666", OPTIONS+="static_node=kvm"`), reloads udev, and then runs `reactivecircus/android-emulator-runner` v2.38.0 with API 30, target `aosp_atd`, and arch `x86_64`. That action installs the system image, boots the emulator, and runs `scripts/android-emulator-connected.sh`. The script uses the runner's `ANDROID_HOME`, installs `platforms;android-35` and `build-tools;35.0.0` when they are missing, installs the pinned Gradle, and runs `:backup:connectedDebugAndroidTest` and `:host:connectedDebugAndroidTest`. It does not start a second emulator. The backup test inserts a generated one-pixel JPEG with synthetic GPS EXIF, reads it with `setRequireOriginal`, PUTs it to a loopback WebDAV, and checks that the received file's Exif APP1 segment is byte-identical to the source. The MediaStore row stays, with the same bytes. The host test launches `HostActivity` and checks that the first verified copy lands within 5 minutes of that setup. A closed port and a SHA-256 mismatch each appear on the status screen and as notification `1001`, with a failure count above zero. A blank status or a missing notification fails the job. The job does not publish an APK. A machine with its own KVM can boot the same image locally with `scripts/android-emulator-ci.sh`, which then calls the connected script.

The round-trip job also runs on `macos-14` (Apple silicon, arm64) and `windows-latest`. Those legs run `cargo fmt`, `cargo clippy`, and `scripts/with-minio.sh cargo test --locked --all-targets`, the same suite as Ubuntu, including the read-only source snapshot, the in-process scale tests, and the S3 and rclone round-trips. Docker is not used. The million-item raid stays on its weekly workflow.

`scripts/with-minio.sh` downloads a pinned MinIO binary. macOS uses `minio.darwin-arm64.RELEASE.2025-09-07T16-13-09Z`, SHA-256 `7c3b3039b76e55a1b80935848ed83998d5e8d317374f87851f46a019ff5c0aa4`. Windows uses `minio.windows-amd64.RELEASE.2025-09-07T16-13-09Z.exe`, SHA-256 `af709e6ba68488404e85acdd22a3030d0f5e56a108d4b27d744f18ceb50861b4`. `scripts/install-rclone.sh` downloads `rclone-v1.75.2-osx-arm64.zip`, SHA-256 `610ab7d48615135dfc60b763858b11a426a0d3d1160c1bb76fb0ae6011b02edd`, and on Windows `rclone-v1.75.2-windows-amd64.zip`, SHA-256 `8a9db2bad1dc79a65b3348fd857069598e2aab7cf4d118b77b1df23055aff818`. ExifTool is the same 13.59 tarball. Windows installs Strawberry Perl so that tarball can run, then the script checks the tarball checksum. An OS without a pinned MinIO binary does not start Docker. The script prints that S3 will not run, sets `ALBUMEN_S3_UNAVAILABLE=1`, and the S3 tests return before they would panic. Ubuntu, macOS, and Windows each have a pinned binary and run the full suite.

Windows paths longer than 260 characters use the `\\?\` prefix. Reserved device names (`CON`, `PRN`, `AUX`, `NUL`, `COM1`–`COM9`, `LPT1`–`LPT9`) use that prefix too. A destination that already has the same name in another case is an error. Named NTFS alternate data streams are copied with the file. Modification time is kept to the 100 ns tick NTFS stores.

The round-trip job also runs on `windows-2025`. That label is pinned. It is not `windows-latest`. The job uses Git Bash and sets `core.autocrlf` to false before checkout so `cargo fmt` sees LF. It runs `cargo fmt`, `cargo clippy`, and `scripts/with-minio.sh cargo test --locked --all-targets`. `scripts/with-minio.sh` downloads `minio.windows-amd64.RELEASE.2025-09-07T16-13-09Z.exe`, SHA-256 `af709e6ba68488404e85acdd22a3030d0f5e56a108d4b27d744f18ceb50861b4`. `scripts/install-rclone.sh` downloads `rclone-v1.75.2-windows-amd64.zip`, SHA-256 `8a9db2bad1dc79a65b3348fd857069598e2aab7cf4d118b77b1df23055aff818`. ExifTool is the same 13.59 tarball. The `windows-2025` image supplies Perl. `scripts/install-exiftool.sh` keeps that pinned script and writes `exiftool.cmd` beside it. Rust resolves a bare `exiftool` only as `exiftool.exe`, so Albumen launches `exiftool.cmd` on Windows and that launcher runs the pinned script through `perl`. No ExifTool, MinIO, or rclone leg is skipped on this image. An architecture without a pinned Windows binary still sets `ALBUMEN_S3_UNAVAILABLE=1` and stays on the local filesystem.

NTFS stores modification times in 100 nanosecond ticks. `set_mtime` writes that tick and the copy check requires it back. A finer timestamp is not rounded further. The round-trip still requires SHA-256, the filename, `FileModifyDate`, and every embedded EXIF, XMP, IPTC, GPS, and QuickTime tag. ExifTool on Windows reports the creation time as `System:FileCreateDate` from the same stat field Unix reports as `System:FileInodeChangeDate`, so that tag is ignored with the other filesystem identity tags. `System:ZoneIdentifier` is the NTFS `Zone.Identifier` alternate data stream. A byte copy does not carry that stream, and the comparison ignores the tag. Paths inside manifests stay slash-separated. The byte, filename, mtime, and ExifTool round-trip is not skipped on Windows. The extended-attribute identity tests in `cli/tests/source_readonly.rs`, `cli/tests/raid_scale.rs`, `mcp/tests/source_readonly.rs`, and `receive/tests/source_readonly.rs` are Unix-only, because they use `std::os::unix` and the `xattr` crate, which does not build on Windows. Symlink creation uses the Windows symlink API. File identity for a Windows hard link is the NTFS creation time and size of a regular file, because `MetadataExt::file_index` is still unstable. A directory creation time is not an identity: directories created in one tick share it, and a sibling library is not the source. Unix tests use an inode. A hard link of a source file shares that file's creation time and size, so that destination is refused. A manifest file, a receiver sidecar, and a receiver tombstone are fsynced and then renamed. Opening the parent directory to fsync that rename returns access denied for some Windows directories, including the process temp root and a library created under it. After the file sync and the rename, that denial is not a failed write.

`scripts/check-dest-writes.py` runs in the round-trip job before the tests. It fails when production Rust outside `ingest/src/dest.rs` creates, writes, renames, or removes a file. Test modules are stripped first. `bench/` is not scanned: it writes synthetic timing files and does not open a user archive.

`scripts/scan-no-network.sh` runs on `ubuntu-24.04` with rootless podman and strace. It is the socket and source-write proof for `albumen scan` and an `albumen-receive` dry-run. `scripts/sandbox-trial.sh` is the same shape against a copy of `fixtures/`. macOS and Windows runners do not run that rootless container. The seccomp socket denial stays on Ubuntu.

The `zero network` job runs on `ubuntu-24.04`, `macos-14`, and `windows-2025`. It builds a synthetic library and runs default-config `albumen scan`, then default-config `albumen-mcp` (export and upload off) twice: once with a metadata filter, which is the process-local index, and once with a filename search. There is no on-disk catalog. Linux uses `strace -f -e trace=network` and fails on any IPv4 or IPv6 socket, connect, send, or bind, including DNS and a connect from a loopback bind toward an external address. macOS uses `sandbox-exec` with `deny network*` (SIGKILL) and denies the `mDNSResponder` mach lookup. The profile names the physical work directory, because `mktemp` on macOS returns the `/var` symlink. Windows uses `pktmon --process-name` when that filter exists. The `windows-2025` inbox `pktmon filter add` has no process filter, and a machine-wide capture would include the runner, so that leg blocks outbound traffic from `albumen.exe`, `albumen-mcp.exe`, and `perl.exe` and audits Filtering Platform failures (events 5152 and 5157). The canary has to show a blocked connect to `203.0.113.5` and a blocked DNS send to that address on port 53. Windows Firewall does not classify a loopback destination, so a UDP send to `127.0.0.1:53` is absent from that audit and the log names it. A canary connection has to be visible to the observer before the three commands count. The source file's SHA-256 and mtime stay unchanged.

`scripts/no-unexpected-egress.sh` runs in that same job. It puts `albumen`, `albumen-mcp`, and `albumen-receive` in a user network namespace and straces them. A connection to any address other than the destination that command was given fails the job. A dry-run names no destination. `export --apply` to `s3://` may connect to `ALBUMEN_S3_ENDPOINT`. `albumen-receive --apply` may bind its listen address.

The generated million-item tree is `cli/tests/raid_scale.rs`. It is `#[ignore]`, so a pull request does not create a million inodes and does not wait on that job. [`.github/workflows/raid-scale.yml`](../.github/workflows/raid-scale.yml) runs it on `macos-14` with `--ignored`, on `workflow_dispatch` and a weekly schedule. The job timeout is 180 minutes. The workflow does not set `ALBUMEN_RAID_ITEMS`. The ladder these jobs belong to is [test-ladder.md](test-ladder.md). What each binary can read, write, and reach is [threat-model.md](threat-model.md).

`.github/workflows/macos-binaries.yml` builds `albumen`, `albumen-mcp`, and `albumen-receive` for x86_64 and aarch64 on Linux (gnu), Windows (MSVC), and macOS. The archives are `albumen-linux-x86_64`, `albumen-linux-aarch64`, `albumen-windows-x86_64`, `albumen-windows-aarch64`, `albumen-macos-arm64`, and `albumen-macos-x86_64`. Each upload includes the `.tar.gz`, a sibling `.sha256`, keyless cosign bundles, and GitHub artifact attestations. `SHA256SUMS` is inside the archive. The workflow filename stays `macos-binaries.yml` so the certificate identity path stays the same. A `v*` tag runs it. `workflow_dispatch` takes a release tag and defaults to `v0.1.0`. The upload uses `gh release upload --clobber` and does not move the tag. The build is reproducible-ish and is not claimed bit-identical. Verification and the Gatekeeper notes are in [release-verify.md](release-verify.md). The trial commands are in [trial-macos.md](trial-macos.md).

The install job does not install a Rust toolchain. A package job on `ubuntu-24.04`, `macos-14`, and `windows-2025` builds the release archive for that runner and uploads it. The install job downloads that artifact (the same layout as a GitHub release asset, which is what `scripts/install.sh` uses when `ALBUMEN_ARCHIVE` is unset). It runs `scripts/check-quickstart.py`, which fails when `scripts/quickstart.json` has more than five steps or the verify step does not check SHA-256. `scripts/check-install.sh` rejects a bad checksum, a bad inner `SHA256SUMS`, a rejected cosign bundle, and a rejected `gh attestation` without copying binaries. The quickstart then installs those binaries and PUTs one synthetic file to a local `albumen-receive` with `X-Albumen-Mtime`, the same header a phone sends. The job fails unless the response `X-Albumen-Sha256`, the stored file, and the source are the same digest and the source mtime is unchanged. Windows runs `scripts/install.ps1` and `scripts/quickstart.ps1` for that path. The latest GitHub release is not required to contain every archive; the PR artifact is the archive under test.

The iOS package job runs `swift test --package-path mobile/ios` on `macos-14`. PhotoKit is a macOS framework, so the package builds there. This VM is Linux and cannot link Photos. If the macOS runner is rejected for billing, that job has to come out and this page has to say so.

A second macOS job, `ios background upload`, runs `scripts/ios-xcode.sh` on `macos-14` only. `xcodebuild` builds the `Albumen` host and the `AlbumenBackgroundUpload` extension for generic iOS with code signing off. The job does not run on Ubuntu, and it does not publish an app.

A third macOS job, `ios simulator backup`, runs `scripts/ios-simulator.sh` on `macos-14` only. It builds `albumen-receive`, listens on `127.0.0.1:18080`, boots an iPhone simulator, and runs `AlbumenSimulatorTests` inside `AlbumenSimulatorHost`. That host allows cleartext HTTP to the loopback receiver. It is not the camera-roll app, and it does not embed the upload extension. The test saves the receiver and the Keychain password, then uploads a synthetic GPS JPEG with a foreground session. That session uses the same PUT, the same Keychain challenge, and the same SHA-256 verdict as the background session. The received file's Exif APP1 segment has to match the source, and the verified copy has to land within 5 minutes of that setup. A closed port and a response whose `X-Albumen-Sha256` is not the file's digest each have to appear in `albumen-backup-status.txt` and as a local notification. The job ad-hoc signs the host so the simulator can launch it. It does not store a development team, and it does not publish an app. What this run proves, and what it leaves to a device, is in [mobile-ios-backup.md](mobile-ios-backup.md).

`ingest/tests/public_fixtures.rs` downloads two CC0 files at test time and checks the SHA-256 pins in `tests/fixtures/LICENSES.md`: the heic.fyi chart `exif-gps-date.heic`, and raw.pixls.us id 4264 (an Apple iPhone 12 Pro ProRAW DNG). The test copies each file with `copy_verify`, exports that library with `export_tree`, and compares SHA-256 plus `exiftool -a -G1 -b`. Apple maker notes, XMP, and GPS have to be present on the file that carries them, and they have to match the copy. Neither file has an IPTC group. No license-clean HEIC+MOV Live Photo pair was found; the license file names that gap. The bytes are not committed. This is not `ALBUMEN_REAL_CORPUS`.

`scripts/synthetic-live-photo.sh` runs in that same test suite. It asks ffmpeg for one HEVC still and a one-second H.264 MOV, wraps the still in a single-item HEIC container (the CI ffmpeg build has libx265 and no HEIF muxer, and `heif-enc` is not installed), and asks ExifTool to write one shared UUID. The movie gets `Keys:ContentIdentifier`. On the HEIC, `-Apple:ContentIdentifier` does not create a maker-note block, so the script writes a generated block through `-EXIF:MakerNoteApple<=` and ExifTool reports `Apple:ContentIdentifier`. `tests/fixtures/LICENSES.md` describes that block. `ingest/tests/synthetic_live_photo.rs` checks that `discover` pairs the two files and that the bytes and that ExifTool dump survive Takeout import, iCloud import, and `export_tree`. `receive` puts the same pair through WebDAV and checks the stored bytes. `scripts/ensure-ffmpeg.sh` installs a distro ffmpeg only when `libx265` is missing. The generated pixels are a solid color. They are not committed.

`scripts/write-iptc-core.sh` copies the committed CC0 JPEG and HEIC and writes IPTC Core with the pinned ExifTool. The SHA-256 pins are in `tests/fixtures/LICENSES.md`. `ingest/tests/iptc_core.rs` refuses a different hash, then copies each file with `copy_verify`, exports it, and compares SHA-256 plus `exiftool -a -G1 -b`, including the `IPTC` group and `XMP-iptcCore`. The same files are in the fixture manifest, so the corpus round-trip covers them too.

`ALBUMEN_REAL_CORPUS` is not set in CI. `ingest/tests/real_corpus.rs` skips when it is unset, so the job stays green. Set it locally to a directory that contains media files and `sanitized.sha256` in sha256sum form. The test then checks each checksum and copy-verifies every listed file on the local filesystem and on MinIO, including SHA-256, filename, mtime, and an ExifTool dump. Live Photo pairs are detected from a shared ContentIdentifier. Sidecars are detected from the generic XMP and AAE names. Do not commit that directory, and do not put a real filename, checksum, or GPS value in the tree. `real-corpus/`, `fixtures/real-device/`, and `*.real-corpus` are gitignored. The synthetic fixture corpus is the committed files under `fixtures/`.

The `albumen-mcp image` job runs on `ubuntu-24.04`. `scripts/check-mcp-release.py` downloads `https://static.modelcontextprotocol.io/schemas/2025-12-11/server.schema.json` and validates [server.json](../server.json). The description must be the tagline and nothing longer. The version must match `mcp/Cargo.toml` and `ghcr.io/jay-the-maker/albumen-mcp:<version>`. The same script requires the default `/library` mount to be a required read-only bind, and the optional writable mount to be `/destination` rather than the library. The job then builds the Dockerfile and checks the entrypoint, the `io.modelcontextprotocol.server.name` label, and ExifTool. `scripts/check-library-mount.sh` runs that default mount and checks that create, modify, rename, and delete under `/library` fail while the host file stays unchanged. The job does not push.

`.github/workflows/publish-mcp.yml` runs only on a `v*` tag. It repeats the version check against the tag, pushes `ghcr.io/jay-the-maker/albumen-mcp:<version>` with `GITHUB_TOKEN`, installs mcp-publisher v1.8.1 by SHA-256, runs `mcp-publisher login github-oidc`, and publishes `server.json`. Actions in that workflow are pinned to commit SHAs.

Search and browse pagination is covered by `mcp` unit tests, including a synthetic library of one million empty items. That test checks that caption pages and a path query are complete, and that peak RSS stays within 32 MiB from 100,000 items to 1,000,000. The walker computes each path from its index, so the test does not create a million inodes. It finishes in seconds and runs on every pull request inside `cargo test`. A separate nightly job is not used.

The `performance regression` job runs on `ubuntu-24.04` only. It installs the pinned ExifTool and runs `cargo run --release --locked -p albumen-bench -- --check`. The harness repeats each measurement and drops a noisy sample. Runners differ by more than 10 percent in raw MB/s, so the gate compares Albumen with a same-run reference and fails when the copy, cold-search, or browse ratio is more than 10 percent worse than [bench/baseline.json](../bench/baseline.json). Warm search p50 and p95 are printed and are not a failure, because that ratio is not stable on these runners. The library in that job is 128 synthetic items, not 380,000. The budgets and the local 380,000-item command are in [performance-budgets.md](performance-budgets.md).

`philosophy-ack` runs on pull request open, edit, and synchronize. `scripts/check-philosophy-ack.py` reads the pull request body. It fails unless the body contains the checked line `- [x] I have read DESIGN_PHILOSOPHY.md and this change upholds it`, the checked lines `- [x] Sane defaults`, `- [x] No account required`, and `- [x] No nags`, and unless the text under `How this upholds it` is at least 20 characters and is not the template placeholder. HTML comments are ignored, so a checked box or an explanation hidden in a comment does not count. The workflow runs the script's `--self-test` before it reads the pull request. `scripts/check-dco.sh` reads `BASE..HEAD` on the pull request head (not the synthetic merge commit) and fails unless every commit message has a `Signed-off-by` line. It is a script in this repository. It is not a GitHub App.
